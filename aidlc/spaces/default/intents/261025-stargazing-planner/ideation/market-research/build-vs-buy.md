# Build vs Buy — 별 보기 좋은 날 추천 앱

> 이 앱의 실질적인 build-vs-buy 결정은 "앱 자체"가 아니라 그 안의 **데이터**(달 위상·박명, 구름량 예보)를 어떻게 확보하느냐다. intent-statement.md의 핵심 기능(상세 그래프의 달 밝기·구름량·박명)이 이 데이터에 의존한다.

## 결정 대상과 사용자 선호

| 대상 | 선택지 | 사용자 선호 | 잠정 방향 |
|------|--------|-------------|-----------|
| 앱 본체(시각화·추천 흐름) | Build | 차별점이 여기 있음(한 그래프 시각화 + 연휴 카드 추천) [Q2] | **Build** — 이게 앱의 존재 이유 |
| 달 위상·박명 데이터 | 직접 계산(오픈소스 라이브러리) vs 외부 천문 API | 방식 무관, 정확하고 공짜에 가까우면 알아서 [Q3] | **Build(직접 계산)로 잠정** — 외부 의존·비용 최소화 [assumption] |
| 구름량 날씨 데이터 | 외부 날씨 API | 무료/무료 한도 우선 [Q4] | **Buy(외부 무료 API 호출)** — 날씨 예보는 직접 만들 수 없음 [assumption] |

## 판단 근거

- **앱 본체는 Build**: 달 밝기·구름량·박명을 겹쳐 보는 시각화와 연휴 추천 흐름이 이 앱의 차별점이자 만드는 이유다. 기존 도구로 대체되지 않는다. [Q2] (intent-statement.md 차별 가치와 일치)
- **천문 데이터는 직접 계산으로 기운다**: 달 위상·박명은 결정론적으로 계산 가능하고, 사용자가 비용 최소·무료를 선호하므로 외부 API 의존을 줄이는 직접 계산이 유리하다(가설). [Q3] [Q5] [assumption]
- **구름량은 Buy가 불가피**: 미래 날씨 예보는 자체 생성이 불가능하므로 외부 날씨 API가 필요하다. 다만 무료 한도 서비스를 택해 비용 제약(전부 무료)을 만족시킨다. [Q4] [Q5] [assumption]

## 비용·운영 제약

- 전 구성요소를 가능한 한 무료 범위 안에서 운영한다. 특히 날씨 API는 무료 한도 안에서 쓸 수 있는 것을 우선한다. [Q5] [Q4]

## Assumptions & Open Questions

- 천문 데이터의 직접 계산 vs 외부 API 최종 선택, 그리고 구름량 날씨 API의 구체 서비스·무료 한도 적정성은 Feasibility 단계에서 확정한다. [assumption]
