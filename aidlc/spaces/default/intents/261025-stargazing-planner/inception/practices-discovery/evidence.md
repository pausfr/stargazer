## 인터뷰 결정 (Q1–Q7)

- **Q1 작업 방식**: 트렁크 기반, `main` 하나로 단순하게 작업·머지 (답: A).
- **Q2 워킹 스켈레톤**: 특정 선택 없이 맡김 (답: C) → 활성 스코프(feature)의
  기본값에 따르는 것으로 처리. 하드 on/off를 단정하지 않고, Construction에서
  스코프 기본값으로 분류.
- **Q3 테스트 방식·분량**: 전체적으로 가볍게, 핵심 천문 계산 로직 위주
  (답: C). 방법론은 test-after로 확정.
- **Q4 커버리지 기준**: 약 80% 라인 커버리지는 **핵심 계산 모듈에만** 적용,
  UI 등 나머지는 느슨하게 (답: A).
- **Q5 배포 방식**: 맡김 (답: C) → 무료 정적 호스팅(GitHub Pages / Vercel /
  Netlify 무료 티어)에 `main` 머지 시 자동 배포, 별도 운영 승인 게이트 없음.
- **Q6 코드 스타일**: 표준 Prettier + ESLint 설정에 위임, 언어 관용 네이밍
  (답: A).
- **Q7 하드 제약**: 둘 다 (답: C) → ALWAYS 모든 데이터 소스를 무료 범위
  안에서; NEVER API 키 등 비밀값을 클라이언트 번들에 하드코딩.
- **요약 확인**: Consolidated Summary Confirmation에서 "Looks correct"로 확정.

## 미해결 불확실성

- 워킹 스켈레톤 적용 여부는 활성 스코프(feature)의 기본값이 최종 결정하며,
  Construction 단계에서 그 기본값에 맞춰 분류됩니다.
- 무료 날씨 API가 키를 요구하고 정적 클라이언트에서만 호출해야 하는 경우,
  키 노출을 피하는 방식(공개 가능한 키 범위 제한 또는 프록시 필요 여부)은
  설계 단계에서 확정해야 합니다. 이는 NEVER(클라이언트 번들 시크릿 하드코딩)
  제약과 직접 맞물립니다.
- 정적 호스팅 제공자(GitHub Pages / Vercel / Netlify) 중 무엇을 쓸지는 배포
  설계에서 확정됩니다.
